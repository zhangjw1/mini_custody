# Mini Custody MVP 产品范围

## 1. 产品定义

Mini Custody 是一个 Web 版托管钱包学习项目。平台集中保管并使用签名密钥，为预置用户分配链上地址，并允许用户充值和提取测试资产。

项目重点是区块链钱包工程能力，而不是交易所通用业务功能。它用于完整展示小型托管钱包平台的设计、开发和运行过程。

## 2. 项目目标

MVP 必须展示以下能力：

- 确定性钱包和地址生成；
- 平台集中托管密钥并签名交易；
- 支持 EVM、Solana 和 Bitcoin 三种主流链及其不同的账户、签名和交易模型；
- 扫描区块、识别充值、跟踪确认数并幂等入账；
- 构建、签名、广播提币交易并跟踪确认状态；
- 处理代币和资金归集；
- 服务重启后能够安全恢复处理；
- 通过 Web 页面观察钱包工作流和真实链上状态。

## 3. 非目标

MVP 不包含：

- 注册、登录、身份认证和角色权限；
- 提币审核和多人审批；
- KYC、AML、地址筛查和通用风控系统；
- 订单簿、撮合、行情、法币支付和结算；
- 移动端或桌面客户端；
- 主网资产、真实资金和本地区块链模拟环境；
- 生产级 HSM 或 MPC；
- 大量公链接入；
- 完整财务会计或总账系统。

用户采用本地预置的演示数据，在 Web 页面直接选择。这是有意设置的 MVP 边界，不代表正式产品的认证方案。

## 4. 网络和资产范围

完整 MVP 使用三条公开测试网络：

| 网络 | 环境 | 资产 | 模型 |
| --- | --- | --- | --- |
| Ethereum | Sepolia | 原生 ETH、测试 ERC-20 | EVM 账户/代币模型 |
| Solana | Devnet | 原生 SOL、测试 SPL Token | Solana 账户模型 |
| Bitcoin | 默认公共 Signet | BTC | UTXO 模型 |

网络选择依据：

- [Ethereum 官方文档](https://ethereum.org/developers/docs/networks/)将 Sepolia 作为应用开发的默认推荐测试网；
- [Solana 官方文档](https://solana.com/docs/references/clusters)建议应用开发者使用 Devnet，Testnet 主要用于验证器和网络压力测试；
- [Bitcoin Signet](https://bitcoinops.org/en/topics/signet/)是当前更适合应用层开发的公共测试网络，出块比工作量证明测试网更稳定。

系统不得依赖 Anvil、Regtest 或 Solana 本地验证器完成正常充提。RPC 服务必须可以配置，并允许从公共限流端点切换到第三方专用端点。测试币没有真实价值，但助记词和私钥仍必须按敏感数据处理。

## 5. 核心能力

### 5.1 托管钱包

- 创建或导入平台钱包根密钥；
- 为预置用户派生并分配充值地址；
- 私钥材料不得出现在 Web 页面、公开接口和普通日志中；
- 平台代表用户签署提币和归集交易。

### 5.2 充值

- 展示用户专属充值地址；
- 通过扫描区块发现转入交易；
- 跟踪待确认充值；
- 达到配置确认数后只入账一次；
- 重启后从持久化扫描点继续工作。

### 5.3 提币

- 从 Web 页面接收目标地址和金额；
- 广播前拒绝无效地址和余额不足请求；
- 自动构建、签名并广播链上交易；
- 跟踪交易直至成功或失败；
- 在用户余额和历史中反映提币的待处理与最终状态。

### 5.4 资金归集

- 将用户充值地址的资产转移至平台归集地址；
- 分别实现 ETH、ERC-20、SOL、SPL Token 和 BTC 的归集规则；
- 页面可查看每次归集及其链上交易状态。

### 5.5 最小余额账本

平台必须维护足够的内部状态，防止重复入账和超额支出。系统需要提供可用余额、待确认充值、待处理提币以及不可变的余额流水。

MVP 不实现完整财务会计系统。

### 5.6 链状态可观测性

- 展示各测试网 RPC 连接状态和网络最新高度；
- 展示系统最后成功扫描的区块；
- 展示充值、提币、归集、交易哈希和确认数；
- 记录可在 Web 页面检查的处理失败信息。

## 6. Web 页面范围

MVP 只提供一个 Web 应用，不拆分移动端或独立管理后台。

| 页面 | 用途 |
| --- | --- |
| Dashboard | 各测试网状态、扫描进度、归集钱包余额、最近活动 |
| Accounts | 选择预置用户，查看地址和余额 |
| Deposit | 展示充值地址、到账状态和确认进度 |
| Withdraw | 提交提币并跟踪生命周期 |
| Transactions | 查看充值、提币、归集、交易哈希和失败信息 |

页面是实际可操作的产品界面。某条链的工作流完成后，页面必须展示真实系统状态，不得继续依赖静态演示数据。

## 7. 交付阶段

### 第一阶段：原生 ETH 纵向闭环

- 托管根密钥和地址派生；
- 原生 ETH 充值扫描和确认；
- 最小余额和流水；
- 原生 ETH 自动提币；
- 覆盖完整工作流的 Web 页面；
- Sepolia RPC、测试币和区块浏览器集成。

### 第二阶段：ERC-20

- 代币配置；
- `Transfer` 事件扫描；
- 代币充值和提币；
- 代币归集及原生币 Gas 处理。

### 第三阶段：Solana

- Solana Ed25519 密钥和地址派生；
- Devnet 原生 SOL 充值识别和确认；
- SOL 交易构建、签名、广播和状态跟踪；
- SOL 资金归集；
- 后续扩展 SPL Token 充提和归集。

### 第四阶段：Bitcoin

- Bitcoin 地址派生；
- 默认公共 Signet 扫描和确认；
- UTXO 发现和选择；
- 交易构建、找零、签名和广播；
- BTC 归集。

### 第五阶段：系统韧性

- 链重组处理；
- 卡住交易和重试策略；
- 对账页面；
- RPC 限流、网络重置、节点及扫描器故障演练。

每个阶段开始实现前，都需要独立完成需求、技术设计和任务文档。

## 8. MVP 完成标准

预置用户能够在 Sepolia 接收 ETH 和 ERC-20、在 Solana Devnet 接收 SOL、在 Bitcoin Signet 接收 BTC；每笔充值都能在确认后被发现并入账；每种资产都能通过平台托管密钥签名并提取；资金能够归集到平台地址；Web 页面能够展示每个操作和对应区块浏览器记录的真实状态。

系统必须在进程重启后保持数据一致，并且绝不能对同一笔链上转账重复入账。
