# 001 - Sepolia 原生 ETH 托管钱包需求

## 1. 目的

本文定义 Mini Custody 的第一个可运行版本：在 Ethereum Sepolia 公开测试网上跑通原生 ETH 托管钱包的完整工作流。

本文只描述外部可观察的产品行为。系统架构、依赖库、数据库表、API 形式和前端框架将在后续技术设计文档中确定。

## 2. 范围

本阶段包含：

- 预置演示用户；
- Ethereum Sepolia 公开测试网；
- 可配置的 Sepolia JSON-RPC 服务；
- 一个由平台控制的钱包根密钥；
- 每个演示用户一个原生 ETH 充值地址；
- 原生 ETH 充值发现和确认；
- 最小用户余额和余额流水；
- 原生 ETH 自动签名和提币；
- 在 Web 页面展示交易和扫描状态；
- 服务重启后安全恢复充值和提币处理。

本阶段不包含 ERC-20、Solana、Bitcoin、自动归集、合约内部 ETH 转账追踪、身份认证、审核流程、主网、HSM、MPC、本地开发链和链重组恢复。

## 3. 术语

| 术语 | 含义 |
| --- | --- |
| 演示用户 | 预先写入本地数据，并在 Web 页面直接选择的用户 |
| 充值地址 | 平台控制并分配给演示用户的链上地址 |
| 可用余额 | 已确认且可以提取的资金 |
| 待确认充值 | 已发现但尚未达到确认数的资金 |
| 待处理提币 | 已被提币流程占用但尚未完成的资金 |
| 确认数 | 包含交易的区块及其后续已接受区块所形成的确认进度 |

## 4. 必须支持的用户流程

### 4.1 查看钱包

1. 操作者选择一个演示用户。
2. 系统展示该用户的充值地址。
3. 系统展示可用余额、待确认充值和待处理提币。
4. 系统展示最近的充值和提币记录。

### 4.2 充值 ETH

1. 从拥有 Sepolia 测试 ETH 的外部地址向用户充值地址发送 ETH。
2. 扫描器发现该转账并创建一笔待确认充值。
3. 页面展示交易哈希、区块高度、金额和确认进度。
4. 达到配置的确认数后，充值变为已确认。
5. 该金额从待确认充值转为可用余额，并且只能入账一次。

### 4.3 提取 ETH

1. 操作者选择用户并填写目标地址和提币金额。
2. 系统展示预估网络费和所需总余额。
3. 操作者提交提币。
4. 系统校验请求并占用所需的用户余额。
5. 平台不经过审核，自动签名并广播交易。
6. 页面展示交易哈希和生命周期状态。
7. 达到确认数后，提币完成并最终结算占用金额。
8. 如果交易无法构建或广播，提币失败，并释放可以安全退回的占用余额。

## 5. 功能需求

### 5.1 演示用户和地址

- **EVM-WAL-001**：系统必须提供至少两个预置演示用户。
- **EVM-WAL-002**：每个演示用户必须拥有一个稳定且由平台控制的原生 ETH 充值地址。
- **EVM-WAL-003**：充值地址必须从平台钱包根密钥确定性派生，并且不得重复。
- **EVM-WAL-004**：使用相同钱包根密钥重新初始化应用时，必须得到相同的用户地址。
- **EVM-WAL-005**：私钥、助记词和解密后的钱包根密钥不得出现在 Web 响应、普通应用日志或交易历史中。

### 5.2 链和扫描器状态

- **EVM-SCN-001**：系统必须展示配置的节点是否可连接。
- **EVM-SCN-002**：系统必须展示节点当前区块高度和最后成功扫描的区块高度。
- **EVM-SCN-003**：扫描器必须按区块高度升序处理区块。
- **EVM-SCN-004**：扫描器必须持久化已完成区块的检查点。
- **EVM-SCN-005**：服务重启后，扫描器必须自动继续工作，不得要求人工执行全量重扫。
- **EVM-SCN-006**：重复扫描已经处理的区块或转账时，不得创建重复充值或重复余额入账。
- **EVM-SCN-007**：RPC 超时、限流或扫描临时失败时，页面必须可观察到失败，并且检查点不得越过尚未正确处理的数据。
- **EVM-SCN-008**：首次启动时必须能够配置扫描起始区块，不得强制从 Sepolia 创世区块开始扫描。
- **EVM-SCN-009**：系统必须校验 RPC 返回的 Chain ID 为 Sepolia，网络不匹配时拒绝启动链上任务。
- **EVM-SCN-010**：RPC 返回限流或临时服务错误时，系统必须延迟重试，不得将其当作不存在区块或交易。

### 5.3 充值

- **EVM-DEP-001**：系统必须识别通过普通 Sepolia 顶层交易直接转入所有已分配充值地址的原生 ETH。合约执行过程中产生的内部 ETH 转账不属于本阶段范围。
- **EVM-DEP-002**：发现充值时，必须记录用户、地址、交易哈希、区块高度、金额和当前状态。
- **EVM-DEP-003**：充值必须先进入 `CONFIRMING` 状态，未确认资金不得增加可用余额。
- **EVM-DEP-004**：Sepolia 所需确认数必须可以配置。
- **EVM-DEP-005**：达到确认数后，充值必须依次转为 `CONFIRMED` 和 `CREDITED`。
- **EVM-DEP-006**：每笔充值只能增加一次可用余额。
- **EVM-DEP-007**：所有金额必须保持链上精度，不得因二进制浮点运算而改变资产数值。

充值生命周期：

```text
DETECTED -> CONFIRMING -> CONFIRMED -> CREDITED
```

### 5.4 余额和流水

- **EVM-BAL-001**：系统必须展示每个用户的可用余额、待确认充值和待处理提币。
- **EVM-BAL-002**：提币不得使用待确认充值资金。
- **EVM-BAL-003**：提币金额加预估网络费超过可用余额时，系统必须拒绝请求。
- **EVM-BAL-004**：每次已确认的余额变化都必须产生持久化流水，并关联对应充值或提币。
- **EVM-BAL-005**：并发请求不得重复花费同一份可用余额。

### 5.5 提币

- **EVM-WDR-001**：提币请求必须包含演示用户、目标地址和大于零的 ETH 金额。
- **EVM-WDR-002**：目标 Ethereum 地址格式错误时，系统必须在创建提币前拒绝请求。
- **EVM-WDR-003**：提交前必须展示收款金额和预估网络费。
- **EVM-WDR-004**：签名或广播前，系统必须占用提币金额和预估网络费。
- **EVM-WDR-005**：平台必须使用托管密钥签署交易，且不得暴露密钥材料。
- **EVM-WDR-006**：广播成功后必须保存交易哈希。
- **EVM-WDR-007**：系统必须持续跟踪已广播交易，直至达到配置的确认数。
- **EVM-WDR-008**：提币确认后，必须按照实际转账金额和实际网络费完成余额流水结算。
- **EVM-WDR-009**：广播成功前失败的请求不得永久占用用户资金。
- **EVM-WDR-010**：使用相同客户端幂等标识重复提交时，最多只能创建一笔链上交易。
- **EVM-WDR-011**：同一地址发出的多笔交易不得使用相同 Nonce。

提币生命周期：

```text
CREATED -> SIGNING -> SIGNED -> BROADCASTED -> CONFIRMING -> COMPLETED
    |          |                    |
    +----------+--------------------+-> FAILED
```

### 5.6 Web 页面

- **EVM-UI-001**：操作者必须能够在不登录的情况下选择演示用户。
- **EVM-UI-002**：账户页面必须展示用户地址和三类余额。
- **EVM-UI-003**：充值页面必须展示可复制地址和真实充值确认进度。
- **EVM-UI-004**：提币页面必须能够校验输入、展示预估费用、提交请求并显示后续生命周期。
- **EVM-UI-005**：交易页面必须区分充值和提币，并按情况展示金额、状态、哈希、区块、确认数以及 Sepolia 区块浏览器链接。
- **EVM-UI-006**：Dashboard 必须展示 Sepolia RPC 连接状态、网络高度、扫描高度和最近的处理失败。

## 6. 失败和重启要求

- Sepolia RPC 不可用、超时或限流不得改变已确认用户余额。
- 扫描器重启不得造成重复充值入账。
- API 重试不得造成重复提币。
- 广播后进程重启，系统必须使用已记录的交易哈希继续跟踪确认状态。
- 广播失败时，必须保留足够的诊断信息定位失败阶段，同时不得泄露密钥材料。
- RPC 提供商临时返回不一致高度时，系统不得跳过尚未可靠处理的区块。
- 第一阶段暂不支持的复杂故障必须显式展示，不得通过伪造链上状态或人工修改数据库掩盖。

链重组处理明确推迟到系统韧性阶段。

## 7. 验收场景

以下场景必须能够在全新的应用数据环境中连接 Sepolia 完整演示。测试依赖公开网络出块，不要求系统控制出块时间。

### 场景 A：确定性地址

- 使用固定开发根密钥启动系统并记录两个用户地址。
- 使用同一根密钥重启系统。
- 验证两个地址保持不变且互不相同。

### 场景 B：确认充值

- 向演示用户地址发送原生 ETH。
- 在达到确认数前，验证充值显示为确认中。
- 等待 Sepolia 产生足够区块后，验证可用余额准确增加一次。
- 重启并重扫相关区块，验证余额不会再次增加。

### 场景 C：成功提币

- 先通过已确认充值为演示用户增加余额。
- 向另一个 Sepolia 地址提交有效提币。
- 验证资金被占用，交易完成签名和广播，并显示交易哈希。
- 等待 Sepolia 产生足够区块使交易确认。
- 验证收款金额、实际网络费、最终余额和余额流水。

### 场景 D：无效提币和余额不足

- 提交格式错误的目标地址，验证系统没有签名交易。
- 提交超过可用余额的金额，验证系统没有签名交易。
- 使用同一幂等标识提交两次，验证最多只存在一笔链上交易。

### 场景 E：重启恢复

- 广播一笔提币，在交易确认前停止应用。
- 重启应用并等待 Sepolia 达到所需确认数。
- 验证原提币进入 `COMPLETED`，且没有广播第二笔交易。

## 8. 质量约束

- 必须提供明确命令，在本地启动应用并连接可配置的 Sepolia RPC。
- 自动化测试必须覆盖地址确定性、金额精度、充值幂等、余额占用和提币幂等。
- Sepolia 集成测试必须使用真实 JSON-RPC，但应与不依赖网络的单元测试分开执行。
- 测试环境必须使用独立且明确标记为非生产用途的密钥材料。
- 端到端测试不得假设公共 RPC 永不限流，也不得假设水龙头始终可用。
- 正常充值和提币流程不得依赖人工修改数据库才能完成。

## 9. 推迟到技术设计阶段的决策

技术设计文档需要确定：

- Sepolia RPC 提供商、备用端点和配置注入方式；
- 根密钥的创建、加密、注入和开发环境恢复方式；
- 派生路径和用户地址映射；
- 持久化模型和数据库事务边界；
- 扫描器采用轮询还是订阅；
- 初始扫描区块的确定方式；
- 确认数的准确计算方式；
- 提币资金来源和手续费结算方式；
- Nonce 分配和并发控制；
- 模块和进程边界；
- API 契约和前端框架；
- 集成测试和端到端测试方案。
