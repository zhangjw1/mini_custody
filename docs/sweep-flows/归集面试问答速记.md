## 一、项目怎么讲

### 1.1 一句话介绍（30 秒版）

> 用 Go 实现了一个迷你托管钱包，跑在 Sepolia 测试网和 Bitcoin Signet 上，支持 ETH、ERC-20、BTC 三种资产的充值识别、入账、归集和提现。重点处理了**交易幂等、nonce 管理、Gas 代补、区块回滚**这几类资金安全问题。

### 1.2 技术栈

- Go 1.23 + PostgreSQL 17。没有用消息队列，任务协调靠数据库事务、唯一约束和行锁。
- go-ethereum（EVM 交互与签名）、btcd（BTC 交易构造与签名）、go-bip39 + hdwallet（HD 派生）。
- 助记词用 age 加密存放在文件中，启动时解密。
- EVM 地址按 BIP44 派生：`m/44'/60'/0'/0/i`，index 0 是平台热钱包，同时充当 Gas Station。
- BTC 地址按 BIP84 派生：用户地址 `m/84'/1'/0'/0/i`，平台找零地址 `m/84'/1'/0'/1/0`。

### 1.3 各资产怎么做的

| 资产 | 归集方式 | 要点 |
|---|---|---|
| ETH | **不归集**（隔离子钱包） | 充值留在用户自己的地址，提现时从这个地址直接签名转出 |
| ERC-20 | **Gas Station 补 Gas → 代币转到热钱包** | 先补 ETH，确认后再 transfer；提现从热钱包统一出 |
| BTC | **单输入单输出 UTXO 归集** | 每个充值 UTXO 单独一笔归集交易，转到平台找零地址；提现只花平台 UTXO |

### 1.4 可以展开讲的 6 个亮点 ⭐

1. **先落库，后广播**
   签名后先把 raw tx 和 txid 写进数据库，再广播。重试时永远重发同一笔 raw tx，不重新签名。txid 不变，所以天然幂等。
2. **广播结果不确定（BROADCAST_UNKNOWN）**
   广播失败或超时，不直接判定失败，而是标记为 BROADCAST_UNKNOWN：
   - BTC：先用 `getrawtransaction` 按 txid 查链上；没有的话用 `testmempoolaccept` 预检，再重发原交易；预检被拒就转人工审核。全程不改交易内容，也不释放输入。
   - EVM："already known" 视为成功；遇到 "nonce too low"，就去查所有候选交易的回执。如果 nonce 被占用了，但不是我们的交易上的链，转人工审核。
3. **nonce 管理**
   `nonce = max(链上 pending nonce, 数据库 next_nonce)`，在行锁内分配并自增。用户地址和平台钱包各维护一份。补 Gas 和代币提现共用平台钱包的 nonce 序列。
4. **ERC-20 补 Gas 的串联**
   - 补 Gas 金额 = `gasLimit × maxFee × (1 + 20% 安全系数) − 地址现有 ETH`，有单笔上限（0.005 ETH）。平台钱包还要保留最低余额。
   - 补 Gas 交易**确认后**，归集 worker 才会领取这个归集任务；分配 nonce 时还会再检查一次。
   - 补 Gas 交易在广播**之前**就登记为"内部转账"，扫块服务据此排除它，不会把它当成用户充值入账。
5. **区块回滚**
   扫块服务保存检查点哈希，发现哈希不一致就回退一个确认窗口重新扫描；入账前再校验一次区块哈希。被回滚的充值标记为 ORPHANED，并写一条冲正账（DEPOSIT_REVERSAL）。
6. **交易卡住的处理**
   - 超过 60 秒没进内存池就重发原交易；超过 180 秒没确认就用相同 nonce 加价 15% 替换，最多替换 3 次。
   - 归集交易的加价次数还受补 Gas 安全余量的限制，避免加到地址付不起。

### 1.5 主动说出不足和改进方向（面试官很看重）⭐

| 现状 | 生产上的改进 |
|---|---|
| BTC 单输入单输出，每个 UTXO 一笔交易 | 多输入合并成一笔，按输入数算 vsize，设置经济阈值 |
| BTC 费率是固定配置（默认 2 sat/vB） | 用 `estimatesmartfee` 或 mempool API 动态估算 + 费率上下限 + 手续费上限保护 + RBF |
| ETH 不归集（隔离子钱包） | 优点是简单；缺点是提现受单个地址余额限制，充值地址的私钥都要在线。生产上改成归集到热钱包 |
| worker 领取任务没用 `SKIP LOCKED`，只能单实例部署 | 用 `FOR UPDATE SKIP LOCKED` 领取任务，支持多实例 |
| 没有热转冷和水位管理 | 增加上下限水位、多签冷钱包、冷补热审批流程 |
| 没有链上余额对账 | 定时逐个地址比对链上余额和账本，差异告警 |
| ETH 不追踪内部交易 | 用 trace 接口识别合约转入的充值 |
| 只支持一个 ERC-20 合约 | 做成多币种合约白名单表 |
| 没有提现风控（只校验了地址格式和余额） | 地址白名单 + 新地址冷却期、单笔 / 日累计限额、大额人工审核、KYT（见 Q55） |
| 助记词存在加密文件里 | 改用 HSM / MPC，签名服务和业务服务隔离 |

### 1.6 为什么 ERC-20 归集金额取 `min(链上 balanceOf, 已入账金额)`？

- 只归集**已经确认入账**的部分。还没确认的充值、别人空投进来的币不会被提前转走。
- 能兼容转账扣费代币（实际到账比转账金额少）。
- 归集完还有剩余（已入账 − 已归集）的话，自动生成一个后续归集任务。

## 二、基础概念题

### Q1 ⭐ 什么是资金归集？为什么要归集？

**答题要点**
1. 交易所给每个用户分配一个专属充值地址，用来识别是谁充的钱。结果就是资金分散在海量地址上。
2. 归集 = 定期把这些分散的资金汇总到热钱包。
3. 为什么要做：
   - **提现**：提现由热钱包统一出款；
   - **安全**：汇总后才能把大部分资金转进冷钱包；
   - **管理**：便于对账，减少需要签名的私钥数量。

**追问：为什么不让用户都充值到同一个地址？**
那样就分不清是谁充的。用同一个地址的话，必须让用户在转账时填写 memo / tag，比如 XRP、EOS、TON 就是这么做的。但用户经常忘记填，会产生大量人工找回工作，所以 BTC、ETH 这类链普遍用"一人一地址"。

### Q2 ⭐ 热钱包、冷钱包、Gas 钱包分别是什么？

| 钱包 | 私钥状态 | 用途 | 资金量 |
|---|---|---|---|
| 热钱包 | 在线 | 自动处理提现，接收归集 | 少量（总资产的 2%~5%，或 1~2 天的提现量） |
| 冷钱包 | 离线 / 多签 | 长期保管 | 大部分 |
| Gas 钱包 | 在线 | 只存原生币，替其他地址付手续费 | 很少 |

**追问：热钱包水位怎么管理？**
- 设上限和下限：超过上限，把多出的部分转去冷钱包；低于下限，从冷钱包补充。
- 冷补热需要多人审批、离线签名，所以下限要留足反应时间。

### Q3 归集的完整流程？

充值上链 → 扫块识别 → 等待确认 → 风控（KYT）→ 入账 → 触发归集 →（补 Gas）→ 构造交易 → 签名 → 先落库 → 广播 → 确认 → 核销 → 水位检查 → 热转冷。

### Q4 ⭐ 归集手续费谁出？会扣用户的钱吗？

- **不扣用户的钱**。归集手续费是平台成本，单独记"归集成本"科目。
- 平台通过提现手续费把成本收回来，用户充值是免费的。
- 记账时，归集和补 Gas 都**不写用户账本**。本项目的设计里也明确把用户资金、平台资金、归集和补 Gas 这几类资金隔离开。

### Q5 什么时候触发归集？

- 定时批量 + 金额阈值：只有金额远大于手续费时才值得归集。
- 链上费率低的时段集中归集（尤其是 BTC）。
- 热钱包余额不够提现时紧急归集。

### Q6 什么是 KYT？

KYT 即 Know Your Transaction，链上交易反洗钱分析，常用 Chainalysis、Elliptic 等服务。入账前检查资金来源地址的风险。高风险资金要冻结并转人工处理，**不能归集到热钱包里和其他资金混在一起**。

## 三、通用工程题（与链无关）

### Q7 ⭐⭐ 归集怎么保证幂等？怎么防止重复归集？

**答题要点**
1. **先落库，后广播**：已签名的 raw tx 和 txid 写进数据库之后才广播。
2. **重试只重发原交易**：永远不重新构造、重新签名。同一笔交易的 txid 不变，链上只会执行一次。
3. **状态机 + 带条件的更新**：`UPDATE … WHERE status = 'CREATED'`，状态不对就更新不成功，防止重复推进。
4. **唯一约束兜底**：同一笔充值或同一个 UTXO 只能对应一个归集任务（本项目对 `deposit_id` 和 `utxo_id` 都加了唯一约束）。

**追问：如果先广播后落库，会出什么问题？**
广播成功后、落库之前进程崩了，重启后系统不知道已经发过交易，会重新构造一笔：
- BTC 上是同一个 UTXO 生成了两笔冲突交易，费率不同就互相替换，状态会乱掉；
- ETH 上如果重新取了 nonce，就可能产生两笔都上链的交易。

### Q8 ⭐ 广播超时，不知道发没发出去，怎么办？

- 标记为"广播未知"，不能判定为失败，更不能释放已经占用的资金（UTXO / nonce）。
- 按 txid 去链上查：查到就推进到"已广播"；查不到就重发**同一笔** raw tx。
- 重发时节点返回 "already known" 之类的报错，要当作成功处理。

### Q9 ⭐ 多个 worker 并发，怎么防止同一笔资金被重复使用？

- 领取任务：`SELECT … FOR UPDATE SKIP LOCKED`，每个 worker 拿到的任务互不重复。
- 资源占用：UTXO 加锁定状态和租约（锁定人、锁定到期时间）；nonce 在行锁内分配。
- 状态推进全部用带条件的 UPDATE（`WHERE status = 旧状态`）。

### Q10 ⭐ 归集交易转进热钱包，会不会被扫块服务当成充值？

会，必须专门处理：
- 地址要分类管理：用户充值地址、热钱包、冷钱包、Gas 钱包。
- 内部转账（归集、补 Gas）在**广播之前**就登记下来，扫块服务识别到后排除，不给用户入账。本项目的补 Gas 交易就是这样处理的。

### Q11 ⭐ 区块回滚（reorg）怎么处理？

1. **预防**：确认数足够了再入账（BTC 1~6 个块，ETH 12~64 个块或 finalized，SOL finalized）。
2. **检测**：保存区块哈希链；新块的父哈希对不上，就说明发生了分叉。
3. **恢复**：回退一个确认窗口重新扫描，被回滚的充值标记为孤块，写冲正账。
4. **归集方面**：如果某个充值的输入被双花了，基于它的归集交易也会失效，要同步处理。

### Q12 对账怎么做？

- 逐个地址比对链上余额和账本余额：充值地址、热钱包、冷钱包、Gas 钱包都要比。
- 核对资金是否守恒：`Σ 用户余额 ≤ 平台链上总资产`。
- 手续费和补 Gas 单独记成本，否则账永远对不上。
- 发现差异要告警，并暂停相关的自动出款。

### Q13 ⭐ 归集要用每个充值地址签名，私钥怎么管？

- **HD 钱包**：一个主密钥派生出所有地址，不需要逐个保存私钥。
- **业务服务只拿 xpub**：只能生成地址，不能签名。
- **签名服务**：在 HSM / MPC 里按派生路径临时推导私钥，签完即丢，私钥不出安全边界。
- **签名前校验**：目标地址必须在白名单里（只能转到自己的热钱包），金额必须守恒。

**追问：MPC 和多签有什么区别？**
- 多签是链上机制，需要链本身支持（BTC 的 P2WSH，ETH 的 Safe 合约）。链上能看到多个签名，手续费也更高。
- MPC 是把私钥分成多个分片，链下协同签名，链上看起来就是一个普通签名，所以所有链都能用。

### Q14 归集任务的状态机怎么设计？

`CREATED →（WAITING_GAS）→ SIGNED → BROADCASTED（或 BROADCAST_UNKNOWN）→ CONFIRMING → COMPLETED`，异常分支为 `FAILED` 和 `MANUAL_REVIEW`。

设计要点：
- 每个状态只允许合法的转换，用带条件的 UPDATE 保证；
- 终态不可逆；
- 判断不了的情况一律转人工，**宁可卡住，不能错发**。

## 四、BTC 专题

### Q15 ⭐⭐ BTC 归集和 ETH 归集最大的区别？

- BTC 是 **UTXO 模型**：可以多个输入合并成一笔交易，一笔就归集 N 个地址；手续费从输入里扣，不用补 Gas。
- ETH 是**账户模型**：每个地址只能单独发交易，N 个地址就是 N 笔；手续费从地址自己的余额扣。

### Q16 ⭐⭐ BTC 归集的手续费怎么算？输出金额怎么定？

- `手续费 = vsize × 费率（sat/vB）`
- `vsize ≈ 10.5 + 68 × 输入数 + 31 × 输出数`（P2WPKH）
- `输出金额 = 输入总额 − 手续费`，归集时不设找零。
- 交易里**没有手续费字段**，矿工拿走的就是"输入 − 输出"的差额。
- **手续费只和字节数有关，和金额无关**：归集 10 BTC 和归集 0.01 BTC，只要输入个数一样，手续费就一样。

### Q17 ⭐⭐ 手续费给多了，能退回吗？（陷阱题）

**不能。**
- 手续费在签名时就锁定了，矿工拿走全部差额。之后网络费率下降，只会让交易更快确认，不会少收钱。
- 广播之后只能用 RBF **加价**（BIP125 要求替换交易支付更高的手续费），不能降价。
- 预防办法：签名前再取一次费率；"低开高走"，先给低一点，卡住了再用 RBF 加价；设手续费上限，超过就拒绝签名。

**对比**：ETH 设置的 maxFeePerGas 只是上限，实际按 `gasUsed × (baseFee + tip)` 扣费，多出来的部分不扣。

### Q18 ⭐ 交易卡住了怎么办？

- **RBF**：发一笔花费相同输入、费率更高的交易，把原交易替换掉。
- **CPFP**：接收方再发一笔交易花掉这笔卡住交易的输出，并给出高手续费，矿工为了拿到子交易的手续费，会把父交易一起打包。
- 注意：手续费太低的交易可能被**挤出内存池**，看起来就像消失了，需要重新广播。

### Q19 什么是粉尘？为什么不归集粉尘？

- 粉尘：金额小于花掉它所需手续费的 UTXO。P2WPKH 的粉尘线是 294 sat。
- 归集粉尘，手续费比金额还高，是亏本的。
- **粉尘攻击**：攻击者往大量地址打粉尘，等这些地址合并花费时，就能关联出它们属于同一个实体。
- 本项目：扣完手续费后输出低于 294 sat 的，标记为 FAILED，并释放 UTXO 锁。

### Q20 ⭐ UTXO 为什么要加锁？

- 归集正在花的 UTXO，如果又被提现选中，就会出现双花冲突，其中一笔一定失败。
- 做法：选中后立刻标记为 LOCKED（记录锁定人和到期时间），交易确认后改为 SPENT，失败了就释放。
- 本项目：充值入账的同一个事务里就锁定 UTXO 并创建归集任务；提现只花平台找零地址的 UTXO，和归集完全隔离。

### Q21 什么是未确认交易链问题？

花费一个还没确认的 UTXO，会形成交易链。节点对交易链有长度限制（默认祖先 / 后代各最多 25 个），而且上游一卡，下游全卡。所以提现应优先使用已确认的 UTXO。

### Q22 BTC 签名有什么要注意的？

- 不同脚本类型（P2WPKH / P2TR / P2SH-P2WPKH）的签名方式不一样。
- SegWit 签名会把**输入金额**签进去，金额填错，签名就无效。
- 多方签名之间常用 PSBT（BIP174）传递未签名或部分签名的交易。

## 五、ETH / ERC-20 专题

### Q23 ⭐⭐ nonce 是什么？管理不好会怎样？

- nonce 是账户的交易序号，必须从 0 开始连续递增。
- **出现空洞**：比如 nonce 5 没发出去，那么 6、7、8 全部卡住。
- **重复使用**：相同 nonce 的两笔交易互相替换，只有一笔能上链。
- **节点不可靠**：负载均衡后面的不同节点，返回的 pending nonce 可能不一样。
- **做法**：nonce 由自己的数据库在行锁内分配。本项目取 `max(链上 pending, DB next_nonce)`，既能兼容外部发起的交易，又不会倒退。

**追问：nonce 空洞怎么修复？**
用缺失的那个 nonce 补发一笔交易，比如给自己转 0 ETH，把空洞填上，后面卡住的交易就能继续执行。

### Q24 ⭐ ETH 交易卡住了怎么办？

- 用相同 nonce、更高的费用发一笔替换交易。geth 要求费用至少比原交易高 10%。
- 本项目：超过 60 秒没进内存池就重发原交易；超过 180 秒没确认就加价 15% 替换，最多 3 次，之后转人工。

### Q25 ⭐ EIP-1559 的手续费怎么算？maxFee 怎么设？

- `实际单价 = baseFee + priorityFee`，其中 baseFee 被销毁，priorityFee 给验证者。
- `实际手续费 = gasUsed × 实际单价`，并且不超过 `gasLimit × maxFeePerGas`。
- baseFee 每个块最多上涨 12.5%。常见做法是 `maxFee = 2 × baseFee + tip`（本项目也是这样），足以覆盖连续几个块的上涨。

### Q26 ⭐ 交易执行失败了（status = 0），还扣手续费吗？（陷阱题）

**扣。** 交易执行失败（revert）照样消耗 gas。所以判断成功必须看 `receipt.status = 1`，只看到"已打包"不算成功。

### Q27 ⭐⭐ ERC-20 归集为什么要补 Gas？怎么补？

- 代币余额记在合约里，转代币要调用合约，调用合约需要 ETH 付 Gas。而充值地址只收到了代币，没有 ETH，也就是"有币没油"。
- 流程：估算 Gas → Gas 钱包给充值地址补 ETH → **等补 Gas 交易确认** → 充值地址把代币 transfer 给热钱包。
- 关键点：
  - 补多少：估算值 × 安全系数，减去地址已有的 ETH；
  - 补 Gas 必须幂等，不能重复补；
  - 补 Gas 确认之前绝不发代币转账；
  - 补 Gas 交易不能被扫块服务当成用户充值。

**追问：补 Gas 交易失败了怎么办？**
本项目的做法是：补 Gas 交易被 revert，对应的归集任务直接标记为 FAILED。生产上可以自动重建一个补 Gas 任务，或者转人工处理。

**追问：有没有不用补 Gas 的方案？**
- **CREATE2 转发合约**：充值地址本身就是一个预先计算出的合约地址，由运营账户一笔交易批量部署并转出，Gas 由运营账户付。BitGo 用的就是这种方案。
- **EIP-7702**：充值地址（EOA）签一个委托授权，由赞助方发 type-4 交易代付 Gas，可以批量处理（2025 年 Pectra 升级之后可用）。

### Q28 ⭐ 怎么识别 ERC-20 充值？怎么防假币？

- 用 `eth_getLogs` 过滤 Transfer 事件（topic0），取出 to 字段，和平台地址集合比对。
- **防假币**：只认白名单里的合约地址。任何人都能部署一个名字叫 USDT 的合约。本项目在查询日志时就限定了合约地址，解码时还会再校验一次。
- 金额按 decimals 换算：USDT 是 6 位小数，大多数代币是 18 位。全程用大整数，不用浮点数。

### Q29 USDT 有哪些坑？

- `transfer` **不返回 bool**，是非标准实现，用标准 ABI 解析返回值会出错。判断成功要看 receipt.status 加上 Transfer 事件。
- 有**黑名单**：被冻结的地址无法转出，归集前可以先查 `isBlackListed`。
- 本项目判断归集成功的条件：receipt 成功，并且有一条从用户地址到热钱包、金额精确匹配的 Transfer 事件，否则标记为 HOT_WALLET_CREDIT_MISSING。

### Q30 什么是内部交易？为什么会漏扫？

- 合约在执行过程中转出的 ETH（比如其他交易所的批量提币合约、多签钱包）不是一笔独立的交易，普通的交易列表里看不到。
- 要用 `debug_traceBlock` 之类的 trace 接口，或者用余额变化来识别。
- 本项目目前只识别顶层的 to/value 转账，这是已知的局限。

### Q31 ⭐ 本项目的 ETH 为什么不归集？（项目设计题）

- 设计上选的是"隔离子钱包"：每个用户地址就是一个独立的子账户，提现直接从这个地址签名转出。
- 优点：不需要归集，也没有 dust 问题，逻辑简单，适合演示 MVP。
- 缺点：
  - 提现金额受单个地址余额限制；
  - 所有充值地址的私钥都得保持在线；
  - 资金分散，没法热转冷。
- 生产上应该改成：ETH 归集到热钱包（转出金额 = 余额 − 21000 × maxFee），由热钱包统一出款。

## 六、SOL / SPL 专题

### Q32 ⭐ Solana 归集和 ETH 最大的区别？

- Solana 支持**单独指定手续费付款人（fee payer）**：平台的 Gas 钱包代付手续费，充值地址就能把余额**全部转空**，也不用补 Gas。
- 一笔交易可以包含多条指令，**一次归集多个地址**（受 1232 字节的交易大小限制，一般 8~12 个地址）。
- 手续费：每个签名 5000 lamports，再加可选的优先费，非常便宜。

### Q33 ⭐⭐ blockhash 过期是什么？重发要注意什么？（陷阱题）

- 每笔交易都要带一个最近的 blockhash，大约 60~90 秒（150 个块）后就失效。
- **陷阱**：交易发出后一直没确认，换一个新的 blockhash 重发，结果旧交易也上链了，**同一笔转账执行了两次**。
- **正确做法**：先确认旧交易已经**过期**（当前区块高度 > `lastValidBlockHeight`），并且确实没有上链，才能用新的 blockhash 重建交易。需要离线签名的场景，用 durable nonce。

### Q34 什么是租金（rent）？对归集有什么影响？

- Solana 账户需要保持"免租最低余额"：不存数据的账户约 0.00089 SOL，代币账户约 0.00204 SOL。
- 账户余额**要么为 0，要么不低于这个最低值**，所以转走大部分、只留一点点反而会失败。
- 归集时直接全额转空就行（由 fee payer 付手续费）。Gas 钱包自己也要满足这个最低值。

### Q35 ⭐ SPL 代币存在哪里？ATA 是什么？

- 代币不直接存在钱包地址里，而是存在钱包名下的**关联代币账户（ATA）**里，每种代币一个 ATA，地址由"钱包地址 + mint"推导出来。
- 第一次给某个地址转某种代币时，通常由**发送方**创建 ATA 并支付租金。
- 归集后可以用 `closeAccount` 关闭空 ATA，把租金退回平台。要权衡：关了能拿回租金，不关的话，下次充值时发送方不用再付租金。
- 识别充值：按 mint 白名单防假币；按代币账户的 owner 识别用户，因为用户可能转到的不是 ATA。

### Q36 Solana 地址派生有什么特殊之处？

- 使用 Ed25519 + SLIP-10，**只支持硬化派生**，**不能像 BTC、ETH 那样用 xpub 派生子地址**。
- 结果是：地址必须在有私钥的环境里生成，或者提前批量生成一个地址池。
- 常用路径：`m/44'/501'/i'/0'`。

### Q37 Token-2022 有什么风险？

- **转账手续费扩展**：实际到账金额比转账金额少，要按余额变化入账。
- **transfer hook**：转账时会调用外部程序，可能导致转账失败。
- **冻结权限**：发行方可以冻结账户。
- 新币种上线前，要逐个评估它启用了哪些扩展。

## 七、三链对比题

### Q38 ⭐⭐ 对比三条链的归集

| 维度 | BTC | ETH / ERC-20 | SOL / SPL |
|---|---|---|---|
| 模型 | UTXO | 账户 | 账户 + ATA |
| 手续费由谁付 | 从输入里扣 | 地址自付 / 补 Gas | fee payer 代付 |
| 计费依据 | 字节数 | gas 消耗 | 签名数 |
| N 个地址需要几笔交易 | 1 笔 | N 笔 / ERC-20 经典方案 2N 笔 | 约 N/10 笔 |
| 并发控制 | UTXO 锁 | nonce 串行 | 基本不需要 |
| 交易卡住怎么办 | RBF / CPFP | 相同 nonce 加价替换 | 确认过期后重建 |
| 最怕的事故 | 手续费给多 / 忘加找零 | nonce 空洞 | 过期判断错误导致执行两次 |
| 余额残留 | 无 | dust | 无（要遵守租金规则） |
| 确认 | 1~6 个块 | 12~64 个块 / finalized（约 12.8 分钟） | finalized（约 13 秒） |

### Q39 ⭐ 三条链的归集手续费分别怎么算？

- BTC：`vsize × 费率`。签名时就锁定，多给了不退。
- ETH：`gasUsed × (baseFee + tip)`。ETH 普通转账固定 21000 gas，ERC-20 转账约 4.5 万~6.5 万 gas。
- SOL：`签名数 × 5000 lamports + 优先费`，由 fee payer 支付。

## 八、场景设计题

### Q40 ⭐⭐ 让你设计一个交易所的归集系统，怎么设计？

按模块讲：
1. **地址服务**：HD 派生，业务服务只持有 xpub；地址分类（充值 / 热 / 冷 / Gas）。
2. **扫块服务**：每条链一个扫块器，保存区块哈希检查点、处理回滚、按确认数分级。
3. **账务风控**：KYT、入账、冲正；内部转账不入用户账。
4. **归集服务**：
   - 策略：定时 + 阈值 + 费率时段；
   - 状态机；
   - 先落库后广播；
   - 用 `SKIP LOCKED` 领取任务；
   - 每条链各自的适配：BTC 多输入合并、ETH nonce 管理、ERC-20 补 Gas、SOL 用 fee payer。
5. **签名服务**：HSM / MPC；签名前校验目标地址白名单和金额上限。
6. **热冷管理**：水位、多签冷钱包、冷补热审批。
7. **对账与监控**：链上余额 vs 账本；告警指标包括卡单数、Gas 钱包余额、手续费异常、扫块延迟。

### Q41 Gas 价格突然暴涨，怎么办？

- 暂停小额归集，只归集大额或紧急的；
- 补 Gas 和归集都设单价上限，超过上限就等待；
- 已经卡住的交易，评估是加价替换还是继续等；
- 确保热钱包有足够余额支撑提现，必要时冷补热。

### Q42 发现热钱包被盗，怎么应急？

1. 立即暂停所有自动出款（提现、归集、热转冷）；
2. 把热钱包剩余资金转移到新的安全地址；
3. 轮换密钥，归集目标改成新热钱包；
4. 盘点损失、对账；判断用户资产是否受影响，由平台垫付；
5. 复盘：限额、白名单、审批流程哪里失效了。

### Q43 归集任务一直失败或卡住，怎么排查？

按状态定位：
- 卡在 WAITING_GAS：查补 Gas 交易、Gas 钱包余额；
- 卡在 SIGNED / BROADCAST_UNKNOWN：查节点连通性、交易是否被拒；
- 卡在 BROADCASTED：查手续费是否太低、nonce 是否有空洞。

### Q44 大量小额充值（比如几万个地址，每个都只有几 U），怎么归集？

- 不值得逐个归集，设经济阈值，等余额累积够了再归集；
- BTC 在低费率时段合并成批量交易；
- ERC-20 用 CREATE2 或 EIP-7702 批量方案，省掉补 Gas；
- SOL 一笔交易处理多个地址。

## 九、充值与扫块专题

> 完整流程图见 [钱包核心业务流程.md](./钱包核心业务流程.md) 第 1 章。

### Q45 ⭐⭐ 扫块怎么保证不漏块、不重复入账？

**答题要点**
1. **检查点 = 高度 + 区块哈希**：每轮从检查点的下一个块开始扫。新块的父哈希必须等于检查点哈希，对不上就说明分叉了，先回退再扫。
2. **充值记录和检查点在同一个事务里提交**：要么都成功，要么都不成功。扫块中途崩溃，检查点没推进，重启后重扫这一段，不会漏。
3. **重扫不会重复入账，靠唯一约束**：
   - ETH 充值：`UNIQUE (network, tx_hash, address_id)`；
   - ERC-20 充值：`UNIQUE (asset_id, tx_hash, log_index)`；
   - 账本流水：`UNIQUE (entry_type, reference_type, reference_id)`，同一笔充值只能入账一次。
4. **只扫安全深度以内的块**：离链头太近的块容易被回滚，本项目配置了 SafeDepth，最新的几个块先不扫。
5. **单条异常隔离**：某一笔充值处理出错，写入 `worker_errors` 告警后跳过，不阻塞整批入账。

**追问：ERC-20 为什么用 `log_index` 而不是 `tx_hash` 去重？**
一笔交易可以产生多个 Transfer 事件，比如批量转账合约一次给 100 个地址打币。只按 tx_hash 去重，后面 99 笔充值会丢。

### Q46 ⭐ 新生成的充值地址，扫块服务怎么知道？会不会漏？（项目亮点）

- 扫块服务在内存里维护一份"地址 → 用户"的索引，每轮刷新。
- **坑**：按 `id > 上次最大 id` 增量加载会漏地址。自增 ID 在事务开始时就分配了，但提交顺序不一定按 ID 顺序：事务 A 拿到 id=100、事务 B 拿到 id=101，B 先提交，扫块服务读到 101 并把游标推进到 101；随后 A 提交，id=100 永远不会再被加载。
- **本项目的做法（Batch I）**：增量加载时往回多看一个窗口（`id > 最大 id − 回看窗口`），再定期做一次全量刷新兜底。
- 生产上地址多到几百万时，常用 Redis Set 或布隆过滤器做第一层匹配，命中后再查数据库确认。

### Q47 ⭐ `eth_getLogs` 有哪些坑？

1. **范围太大会报错**：节点对一次查询的区块数或返回条数有限制。本项目遇到这类报错就把区间对半拆开，递归重查。
2. **负载均衡后面的节点可能不在同一条分叉上**：getLogs 打到 A 节点，查区块头打到 B 节点，拿到的数据可能来自不同分叉。本项目（Batch I）在 getLogs 返回后清掉这个区间的区块头缓存，重新拉取区块头，**逐条比对日志里的 blockHash**，有一条对不上就当作回滚处理。
3. **`removed = true` 的日志**：说明这条日志所在的块已经被回滚，要当作回滚处理，不能入账。
4. **只认白名单合约**：查询时就限定合约地址，防止假币（见 Q28）。

### Q48 确认数怎么定？

- 本项目跑在测试网，ETH、ERC-20、BTC 默认都是 3 个确认，可以配置。配置校验要求回退块数不小于确认数，否则回滚发生时回退得不够深。
- 生产上的常见做法：
  - BTC：小额 1~2 个确认，大额 6 个；
  - ETH：等 finalized，或者 32~64 个块；
  - TRON：等固化块；SOL：等 finalized。
- **分级确认**：确认数少时先"到账可交易、不可提现"，确认数够了再解冻提现。这样用户体验好，平台风险也可控。
- 确认数还要随链的安全状况调整：小链被 51% 攻击过的，要大幅提高确认数，甚至暂停充值。

### Q49 ⭐ 充值已经入账了，结果区块被回滚了，怎么办？

1. **发现**：本项目除了扫块时检查父哈希，还有一个独立的审计任务（`reconcileCreditedDeposits`），定期复查窗口内**已入账**充值所在区块的哈希是否还在主链上。
2. **冲正**：充值标记为 ORPHANED，写一条冲正流水（DEPOSIT_REVERSAL），从用户余额里扣回。
3. **用户已经把钱提走了怎么办**：余额会变成负数，这时要冻结账户，转人工追偿。这就是为什么**确认数不够的钱不能提现**（见 Q48 的分级确认）。
4. **BTC 只冲正真正变了的**：本项目回退时会逐笔核对充值所在块的最新哈希，只有哈希确实变了才冲正，不会把整个回退窗口内的充值都冲掉。

## 十、提现专题

> 完整流程图见 [钱包核心业务流程.md](./钱包核心业务流程.md) 第 2 章（提现）、第 3 章（风控）、第 4 章（冷热水位）。

### Q50 ⭐⭐ 提现的状态机怎么设计？

**本项目 ETH 提现**：
`CREATED → SIGNING → SIGNED → BROADCASTING → BROADCASTED（或 BROADCAST_UNKNOWN）→ CONFIRMING → COMPLETED`，异常分支为 `FAILED` 和 `MANUAL_REVIEW`。

**本项目 BTC 提现**：在 CREATED 之后多一个 `INPUTS_LOCKED`。先锁定 UTXO，并把选中的输入保存成快照（`selected_inputs_json`），重启后直接复用这份快照签名，不会重新选币。

**生产上通常还会在前面加几步**：`提交 → 风控审核 → 人工审核（大额）→ KYT 检查 → 待出款`，之后才进入上面的签名广播流程。

设计原则和归集一样：带条件的 UPDATE 推进状态、终态不可逆、判断不了一律转人工。

### Q51 ⭐⭐ 提现怎么保证幂等？

分三层讲：
1. **接口层**：客户端每次提现都带一个幂等键（idempotency_key），数据库有 `UNIQUE (user_id, idempotency_key)`。重复请求直接返回原来那笔提现。
   - 本项目还多做了一步：同一个幂等键，但目标地址或金额不一样，直接报幂等冲突，不会悄悄返回旧记录。
2. **执行层**：先落库后广播，重试只重发原交易（同 Q7）。
3. **账务层**：每一笔冻结、结算、释放流水都有唯一约束，同一笔提现的同一种流水只能写一次。

**追问：幂等键由谁生成？**
客户端生成，比如前端在用户点击"提交"时生成一个 UUID，网络重试时带同一个。如果由服务端生成，网络超时后客户端重试，服务端会以为是一笔新请求。

### Q52 ⭐⭐ 提现时余额怎么冻结？手续费怎么预留？（项目题）

**本项目的做法**（ETH 从用户自己的地址出款，所以用户承担真实 Gas）：
1. **冻结**：`可用余额 −= 金额 + 预留手续费`，`提现中余额 += 同样的数`，同时写一条 WITHDRAW_RESERVE 流水。全程在行锁事务里完成，余额不够就直接拒绝。
2. **预留多少手续费**：`gasLimit × (2 × baseFee + tip)`，也就是按最高可能的费用来冻结。
3. **结算**：交易确认后，按实际手续费结算，多冻结的部分退回可用余额，写 WITHDRAW_FINALIZE 流水。
   - 链上执行失败（status = 0）：本金退回，**手续费照扣**（见 Q26）。
   - 实际手续费超过预留：拒绝结算，报错。正常情况下不可能发生，发生了说明有 bug。
4. **加价替换时**：如果需要更多手续费，要在签名之前先追加冻结。

**追问：交易所也是这么收提现手续费的吗？**
不是。交易所从热钱包统一出款，向用户收**固定的提现手续费**（比如提 USDT-ERC20 收 X USDT），和链上实际消耗的 Gas 脱钩，差价是平台的盈亏。本项目是隔离子钱包模式，所以按实际 Gas 收。

### Q53 ⭐⭐ 提现失败了，什么时候可以把冻结的钱退给用户？（陷阱题）

**只有确定这笔交易永远不可能上链时，才能退。**
- 交易一旦签名并发出去，哪怕节点返回了报错，交易也可能已经传播到其他节点。这时退款，交易后来又上链了，就是**双重出款**：用户余额退回了，链上钱也转出去了。
- **本项目的规则**：
  - ETH：只有状态还是 CREATED、**并且还没分配 nonce** 的时候才允许释放冻结，否则直接报错（`ErrUnsafeRelease`）；
  - BTC：只有在广播之前（CREATED / INPUTS_LOCKED）才允许失败并释放余额和 UTXO 锁；
  - 广播之后出了问题，一律转 MANUAL_REVIEW，不释放余额，也不释放 UTXO。
- **广播之后什么时候能确定失败**：
  - ETH：交易上链但 status = 0；或者同一个 nonce 被另一笔交易占用并且已确认；
  - BTC：输入的 UTXO 被另一笔交易花掉并且已确认。

### Q54 ⭐ BTC 提现怎么选 UTXO？找零怎么处理？

**本项目的做法**（`SelectUTXOs`）：
1. 先找**单个就够付**（目标金额 + 手续费）的 UTXO 里**最小的那个**，避免不必要的多输入，手续费最低。
2. 找不到，就按金额从大到小累加，直到够付为止，最多 100 个输入。
3. 找零：如果找零金额低于粉尘线（294 sat），就不设找零输出，把这点零头直接并入手续费，交易也少一个输出。
4. 找零转回平台找零地址；交易确认后，找零作为新的 UTXO 加入平台 UTXO 池。

**行业常见的选币算法**：
| 算法 | 思路 | 特点 |
|---|---|---|
| Branch and Bound（Bitcoin Core 默认先用） | 搜索金额刚好够、不需要找零的组合 | 省一个输出，还不暴露找零地址 |
| 大额优先 | 从大到小累加 | 输入少、手续费低，但小额 UTXO 越积越多 |
| 小额优先 | 从小到大累加 | 能顺便清理碎 UTXO，但当前这笔手续费高 |
| 随机 | 随机选 | 隐私好 |

**取舍**：当前这笔的手续费 vs UTXO 碎片化 vs 隐私。实践中会在低费率时段专门发起"UTXO 合并"交易，把碎 UTXO 合成大的。

### Q55 ⭐ 提现风控一般有哪些？（本项目没做，要主动说出来）

**业务层**：
- 地址白名单；新加的地址有冷却期（比如 24 小时内不能提）；
- 单笔限额、每日累计限额，按用户等级区分；
- 大额提现转人工审核；
- 二次验证：2FA、邮件 / 短信确认；
- 修改密码、换绑手机之后，24 小时内禁止提现；
- KYT 检查目标地址：是否在制裁名单上，是否是混币器、诈骗地址；
- 行为异常：新设备、异地登录、短时间频繁提现。

**系统层**：
- 热钱包出款总额熔断：一段时间内出款超过阈值，自动暂停；
- **签名服务独立校验**：签名服务不信任业务数据库，自己重新校验金额、目标地址、频率。业务库被攻破，也签不出异常交易。

### Q56 提现地址校验要注意什么？

- **EVM**：EIP-55 大小写校验和；本项目统一转成小写存储，比对时不会因为大小写不同而对不上。
- **BTC**：网络前缀不能混用（主网 `bc1`、测试网 `tb1`），还要校验地址类型。
- **TRON**：Base58Check 校验，`T` 开头。
- **Memo 类链**（XRP、TON、EOS）：提到交易所地址时 memo 必填，否则对方无法入账。
- **同地址跨链**：ETH 地址和 BSC、Polygon 地址格式一样，用户选错网络，钱就打到了另一条链上，要在前端反复提示。
- **提到本平台的充值地址**：识别出来后直接走内部转账，在账本里划转，不上链，也不收手续费。

## 十一、TRON 专题

> 归集流程图见 [主流资产归集流程.md](./主流资产归集流程.md) 第 8、9 节；提现流程见 [钱包核心业务流程.md](./钱包核心业务流程.md) 6.2。

### Q57 ⭐⭐ 为什么交易所几乎都要接 TRON？

- **USDT-TRC20** 是 USDT 流通量最大的链之一，转账快、费用比以太坊低得多，支付、OTC、跨境转账大量用它。
- 所以面试时 TRON 的出现频率仅次于 BTC 和 ETH。

### Q58 ⭐⭐ TRON 的带宽和能量是什么？

TRON 没有 Gas，而是用两种资源：

| 资源 | 消耗场景 | 怎么获得 | 没有的话 |
|---|---|---|---|
| **带宽（Bandwidth）** | 每笔交易都消耗，按交易字节数计算 | 每个账户每天有少量免费带宽；质押 TRX 获得 | 燃烧 TRX 抵扣 |
| **能量（Energy）** | 只有调用合约时消耗，比如 TRC20 转账 | 质押 TRX 获得；向别人租赁 | 燃烧 TRX 抵扣 |

- TRX 普通转账只消耗带宽，免费额度通常就够用。
- **USDT-TRC20 转账要消耗几万能量**；收款地址之前没有 USDT 余额时，合约要新写一个存储槽，消耗大约翻倍。
- 没有能量就燃烧 TRX，一笔 USDT 转账可能要好几个甚至十几个 TRX。所以说"USDT-TRC20 转账费贵"，指的是没有能量、直接燃烧 TRX 的情况。
- 获取能量的方式：质押 TRX（Stake 2.0）；在能量市场租赁；把自己质押获得的资源**代理**（delegate）给别的地址。

### Q59 ⭐⭐ TRON 上的 USDT 怎么归集？

和 ERC-20 一样是"有币没油"，但 TRON 有更省钱的做法：
1. **激活账户**：TRON 的新地址只收到 TRC20 时**还没有被激活**，要先给它转一点 TRX 激活，发送方额外付约 1 TRX 的创建账户费用。
2. **代理资源，而不是补 TRX**：平台质押一大笔 TRX，拿到能量和带宽，归集前**把能量代理给充值地址**，归集完再**收回**（undelegate）。TRX 本金不消耗，只是质押锁定。
3. 充值地址调用 USDT 合约的 `transfer`，把币转到热钱包。
4. 成本对比：直接燃烧 TRX ＞ 租赁能量 ＞ 自己质押后代理。量大的交易所都会自己质押。

**追问：代理资源有什么要注意的？**
- 代理和收回本身也是交易，也要消耗带宽；
- 代理出去的资源有锁定期，收回不是即时的，要预留足够的能量池，不能每次都代理刚好够用的量。

### Q60 ⭐ TRON 交易和 ETH 交易有什么不同？（陷阱题）

1. **没有 nonce**。交易里带的是最近一个区块的引用（ref_block_bytes / ref_block_hash）和**过期时间**（expiration，SDK 默认约 60 秒，最长 24 小时）。
   - 好处：同一个地址可以并发发多笔交易，不会有 nonce 空洞；
   - **陷阱**：和 Solana 一样，交易没确认时不能马上重建一笔新的，否则可能两笔都上链。必须先确认旧交易已经过期、并且没有上链。
2. **交易 ID = 交易原始数据的 SHA256**。两笔内容完全相同的交易（同样的收款人、金额、引用块、过期时间）ID 也相同，第二笔会被当成重复交易拒绝。连续给同一个人转同样的金额，要让时间戳不同。
3. **fee_limit**：调用合约时设置的 TRX 燃烧上限。设得太低，能量不够时交易会失败（OUT_OF_ENERGY），**已经消耗的资源不退**。
4. **判断成功**：要查交易回执，`receipt.result = SUCCESS` 才算成功，和 ETH 看 status 是同一个道理。
5. **最终性**：TRON 有 27 个超级代表（SR），每 3 秒出一个块。一个块被 19 个 SR（超过 2/3）后续确认后就**固化**（solidified），不能再回滚，大约 1 分钟。入账以固化块为准。
6. **地址**：Base58 编码、`T` 开头；底层其实就是 20 字节的 EVM 风格地址，加上 0x41 前缀。所以 TRON 可以复用 secp256k1 和 BIP44 派生（coin type 195）。

### Q61 TRON 充值怎么识别？

- **TRX 充值**：遍历区块里的 TransferContract 交易。
- **TRC20 充值**：解析交易回执里的 Transfer 事件日志。只认白名单合约，比如 USDT 的合约地址 `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t`。
- **合约内部转出的 TRX**：要看 internal_transactions，和 ETH 的内部交易问题一样。
- **历史上的"假充值"漏洞**：早期有交易所只检查交易在不在区块里，没检查执行结果。攻击者发一笔执行失败的转账，交易所照样给他入账了。**必须检查 receipt.result**。

## 十二、密钥与安全专题

> MPC 的流程图（DKG、门限签名、分片刷新、与 HD 结合）见 [HD钱包原理与托管实践.md](./HD钱包原理与托管实践.md) 第 7 章。

### Q62 ⭐⭐ 托管系统的私钥是怎么分层保护的？

**本项目**：助记词用 age 加密后存成文件，服务启动时解密到内存里。这是演示级方案，要主动说出不足。

**生产上的分层**：
| 层级 | 存放方式 | 存放资金 | 签名方式 |
|---|---|---|---|
| 冷钱包 | 离线设备 / 多签 / MPC，物理隔离 | 大部分 | 人工审批 + 离线签名 |
| 温钱包 | MPC / HSM，需要审批 | 中等 | 半自动，有审批流程 |
| 热钱包 | HSM / MPC，在线 | 1~2 天的提现量 | 全自动，受策略引擎约束 |

**签名服务的设计要点**：
- 独立部署，网络隔离，只对外提供"签名"这一个接口；
- 内置策略引擎：目标地址白名单、单笔和累计限额、频率限制；
- 不信任上游：业务系统传来的交易，签名服务自己解析，重新校验收款地址和金额；
- 所有签名请求都留审计日志。

### Q63 ⭐⭐ MPC / TSS 的原理怎么讲？

1. **分布式密钥生成（DKG）**：n 个参与方各自生成一个随机数，通过协议算出一个共同的公钥（也就是钱包地址）。**完整私钥从来没有在任何地方出现过**，每一方只拿到一个分片。
2. **门限签名**：任意 t 个参与方（t-of-n）协同计算，直接得出一个标准的 ECDSA / EdDSA 签名。链上看到的就是一个普通签名。
3. **主流协议**：
   - ECDSA：GG18、GG20，之后是 CGGMP21（修复了已知问题，还能识别出是哪一方作恶）；
   - EdDSA（Solana 等）：FROST。
4. **分片刷新**：可以定期刷新所有分片，**公钥和地址都不变**。旧分片泄露也没用。
5. **和 HD 钱包结合**：MPC 支持非硬化派生，所以一个 MPC 根密钥可以派生出大量充值地址（详见 [HD钱包原理与托管实践.md](./HD钱包原理与托管实践.md)）。

**追问：MPC 有什么缺点？**
- 协议复杂，多轮网络通信，签名比单机签名慢；
- 实现上容易出漏洞：2023 年 Fireblocks 披露的 BitForge 漏洞，就影响了多家钱包厂商的 GG18 / GG20 实现，可能导致私钥被提取。

### Q64 ⭐ 多签、MPC、HSM 怎么选？

| 维度 | 多签 | MPC | HSM |
|---|---|---|---|
| 实现位置 | 链上（合约或脚本） | 链下多方协同计算 | 单个硬件设备 |
| 链的支持 | 需要链本身支持 | 所有链都能用 | 所有链都能用 |
| 链上手续费 | 更高（多个签名） | 和普通交易一样 | 和普通交易一样 |
| 隐私 | 链上能看出是多签 | 看不出 | 看不出 |
| 单点风险 | 无 | 无 | 设备本身是单点，要做主备 |
| 调整签名人 | 要改合约或换地址 | 刷新分片即可，地址不变 | 不涉及 |
| 典型用途 | 冷钱包、DAO 金库（Safe） | 托管机构的热钱包和冷钱包 | 银行、传统金融的密钥托管 |

### Q65 ⭐ 怎么从设计上防止热钱包被盗？（预防，区别于 Q42 的应急）

1. **少放钱**：热钱包只放 1~2 天的提现量，多出来的转到冷钱包。被盗了损失也有上限。
2. **签名服务独立校验**：业务系统被攻破，也签不出转到陌生地址的交易。
3. **出款熔断**：一段时间内的出款总额、笔数超过阈值，自动停止出款。
4. **对账告警**：热钱包链上余额和账本对不上，马上告警并暂停出款。被盗往往最先在这里暴露出来。
5. **密钥轮换和最小权限**：运维人员拿不到完整密钥，访问签名服务要多人审批。
6. **供应链安全**：依赖库、构建流程、部署机器都要管控，不少被盗事件是从这里进来的。

### Q66 常见的充值类攻击有哪些？

| 攻击 | 手法 | 防御 |
|---|---|---|
| 假币 | 部署一个叫 USDT 的合约 | 只认合约地址白名单 |
| 假充值 | 交易执行失败，但仍然在区块里 | 检查 receipt.status / result |
| 地址投毒 | 用一个首尾和用户常用地址相同的地址，给用户发 0 金额或小额转账，诱导用户从历史记录里复制错地址 | 过滤 0 金额充值；前端完整显示地址；提现用地址白名单 |
| 回滚双花 | 先在一条分叉上充值，提走之后再让分叉被回滚 | 确认数足够才允许提现（Q48） |
| 粉尘攻击 | 给大量地址打粉尘，追踪地址关联 | 不归集粉尘（Q19） |

## 十三、多链架构与岗位题

> 架构图和上线流程见 [钱包核心业务流程.md](./钱包核心业务流程.md) 第 7、8 章。

### Q67 ⭐⭐ 多链钱包系统怎么抽象？新链怎么接？

**分两层**：
1. **通用编排层（和链无关）**：状态机、幂等、先落库后广播、余额冻结与结算、对账、告警。所有链共用。
2. **链适配层（每条链实现一份）**：

| 接口能力 | 不同链的差异点 |
|---|---|
| 地址派生和校验 | secp256k1 / ed25519；能不能用 xpub 派生；地址编码格式 |
| 扫块 / 识别充值 | 区块交易 / 事件日志 / UTXO；memo |
| 构造交易 | 账户模型 vs UTXO；nonce vs 过期时间 |
| 手续费估算 | gas / vsize / 签名数 / 能量带宽 |
| 广播和确认 | 确认数 / 最终性；替换交易的规则 |

**本项目**：EVM 公共的手续费估算、广播、确认逻辑抽成了共享组件（Batch F2），ETH、ERC-20 提现和归集、补 Gas 都复用它们；BTC 单独一套，因为 UTXO 模型差异太大。

**追问：接一条新链要做哪些事？**
1. 节点：自建还是用第三方 RPC，至少两个节点做容灾；
2. 链的参数：确认数、地址格式、精度、最小充值额；
3. 测试网完整演练充值、提现、归集、回滚；
4. 主网小额灰度，开好监控（扫块延迟、热钱包水位、卡单数）再全量开放。

### Q68 ⭐ 新币种（代币）上线前要评估什么？

- **合约是否可升级**（代理合约）：发行方可以随时改逻辑。
- **黑名单 / 冻结**：USDT、USDC 都能冻结地址。
- **转账扣费**：实际到账比转账金额少，要按余额变化入账。
- **可暂停、可增发**：会影响充提和资产价值。
- **非标准实现**：比如 USDT 的 `transfer` 不返回 bool（Q29）。
- **精度**：decimals 和其他链上的同一个币可能不一样，比如 USDT 在 BSC 上是 18 位。

### Q69 为什么用 Go 写钱包后端？

- 生态最成熟：go-ethereum、btcd、各家公链的官方 SDK 大多有 Go 版本，本项目直接用 go-ethereum 和 btcd 构造和签名交易；
- 并发模型适合扫块、广播这类大量 IO 的后台任务；
- 编译成单个二进制，部署简单，内存占用小；
- 行业里交易所和托管机构的钱包团队以 Go 为主，Java 次之。

## 十四、易错点速记（面试陷阱）

1. ❌ "BTC 手续费多付了会退回" → ✅ 签名即锁定，差额全给矿工；RBF 只能加价。
2. ❌ "ETH 交易失败不扣费" → ✅ revert 照样消耗 gas，要看 `receipt.status`。
3. ❌ "广播超时就算失败，重新构造一笔" → ✅ 标记为广播未知，按 txid 查询，只重发原交易。
4. ❌ "Solana 交易没确认，换个 blockhash 重发" → ✅ 先确认旧交易已过期且没上链。
5. ❌ "按代币名称识别 USDT" → ✅ 只认合约地址白名单。
6. ❌ "归集手续费从用户余额里扣" → ✅ 是平台成本。
7. ❌ "BTC 手续费和转账金额有关" → ✅ 只和交易字节数有关。
8. ❌ "Solana 也能用 xpub 生成地址" → ✅ Ed25519 只支持硬化派生，不行。
9. ❌ "归集到热钱包的钱会被识别成充值" → ✅ 内部转账要提前登记并排除（反过来说，不排除就会出现这个 bug）。
10. ❌ "ETH 用节点的 pending nonce 就行" → ✅ 多节点之间不一致，要由数据库在行锁内分配。
11. ❌ "提现广播报错了，就把冻结的钱退给用户" → ✅ 交易可能已经传播出去；只有确定永远不会上链时才能退（Q53）。
12. ❌ "新地址按 `id > 上次最大 id` 增量加载就行" → ✅ 自增 ID 提交顺序是乱的，会漏地址，要加回看窗口（Q46）。
13. ❌ "ERC-20 充值按 tx_hash 去重" → ✅ 一笔交易可以有多个 Transfer 事件，要按 `tx_hash + log_index` 去重。
14. ❌ "TRON 也有 nonce" → ✅ TRON 用引用块 + 过期时间，重发陷阱和 Solana 一样（Q60）。
15. ❌ "TRC20 转账失败不消耗资源" → ✅ 已经消耗的能量和带宽不退，要看 receipt.result。
16. ❌ "MPC 签名时会把私钥拼起来" → ✅ 完整私钥从生成到签名都不会出现（Q63）。

## 十五、术语速查

| 术语 | 含义 |
|---|---|
| UTXO | 未花费交易输出，BTC 的"零钱" |
| vsize / vB | 虚拟字节，BTC 手续费的计费单位 |
| RBF / CPFP | BTC 交易加速：替换交易 / 子交易带动父交易 |
| PSBT | 部分签名的比特币交易格式（BIP174） |
| reorg | 区块重组，也就是区块回滚 |
| finality | 最终性，区块从此不可回滚 |
| nonce | ETH 账户的交易序号 |
| baseFee / tip | EIP-1559 的基础费（销毁）和小费（给验证者） |
| Gas Station | 给其他地址补 Gas 的钱包或服务 |
| CREATE2 | 可以预先计算出合约地址的部署方式 |
| EIP-7702 | 让 EOA 把代码委托给合约，实现代付手续费 |
| fee payer | Solana 交易的手续费付款人 |
| blockhash 过期 | Solana 交易约 60~90 秒后失效 |
| rent / 免租 | Solana 账户需要保持的最低余额 |
| ATA | Solana 关联代币账户 |
| KYT | 链上交易反洗钱分析 |
| HSM / MPC | 硬件安全模块 / 多方计算门限签名 |
| xpub | 扩展公钥，只能派生地址，不能签名 |
| 水位 | 热钱包余额的上下限阈值 |
| 幂等键 | idempotency_key，客户端生成的请求唯一标识，用于防止重复提现 |
| 安全深度 | 扫块时离链头保留的块数，太新的块先不扫 |
| 带宽 / 能量 | TRON 的两种资源：带宽按字节数计算，能量用于执行合约 |
| 资源代理 | TRON 中把质押获得的能量或带宽借给其他地址使用 |
| 固化块 | TRON 中被超过 2/3 超级代表确认、不可回滚的区块 |
| fee_limit | TRON 调用合约时愿意燃烧的 TRX 上限 |
| DKG | 分布式密钥生成，MPC 中各方生成分片、完整私钥不出现 |
| CGGMP / FROST | MPC 门限签名协议，分别用于 ECDSA 和 EdDSA |
| 地址投毒 | 伪造相似地址的小额转账，诱导用户复制错误地址 |
